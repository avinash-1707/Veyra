**Reusable U3 contracts/interfaces**
- `Order`: immutable item/address/totals snapshots, `status`, `paymentStatus`, `history`, `auditEvents`, `outboxEventIds`.
- Public commands: quote/confirm, `PATCH /v1/orders/:orderId/delivery`, `POST /v1/orders/:orderId/cancel`.
- Domain functions take `shopperId` first and return `{ status, data/message }`; ownership failures intentionally become `404`.
- All API responses use `{ apiVersion: "v1", requestId, data | error }`; Zod schemas validate both input and test responses.
- Mutations need same-origin CSRF headers; replay-sensitive U4 commands should use `idempotency-key`.

**U3 fixture transitions available to unlock U4**
- On confirm: history records `confirmed → preparing`; exposed order status is `preparing`.
- Test-only fulfillment endpoint advances `preparing → shipped → delivered`.
- Cancellation: `preparing → cancelled`; blocked after `shipped`, `delivered`, or already `cancelled`.
- Delivery edits are allowed only in `preparing`.
- Delivery emits `order.delivered`, the architectural trigger for review/return eligibility; the local implementation does not yet derive or persist eligibility.

**Route patterns to implement**
- API architecture already reserves:
  - `POST /v1/orders/:id/returns/eligibility`
  - `POST /v1/returns`
  - `GET /v1/returns/:id`
  - `GET/POST /v1/products/:id/reviews`
  - `POST /v1/support/conversations`
  - `POST /v1/support/actions/confirm`
- Web route convention:
  - Existing `/orders/:orderId`
  - Planned `/orders/:id/returns/:returnId`, `/help`, `/orders/:id/help`
  - Add review entry from delivered order item and product detail.

**Concise implementation plan**
1. Add a U4 contracts file: return eligibility/request/detail, return-history/refund state, review create/list/moderation status, support proposal/confirmation; export it from the contracts barrel.
2. Add focused returns/reviews/support modules; consume owned `Order` snapshots, require `delivered`, append history/audit/outbox records, and keep command idempotency separate per operation.
3. Mount routes in the API root using the established parse → domain call → `commandFailureResponse` → typed envelope pattern.
4. Extend the U3 order fixture with delivered-order helpers or use `advance-fulfillment` in U4 tests; test cross-user denial, duplicate review, expired/prior return, refund transitions, and support confirmation replay.
5. Add API-client helpers and U4 pages/actions from order detail; preserve server-calculated eligibility and direct deterministic actions when support/AI is unavailable.
6. Update progress records after implementation as required by the project guide.

**Policy gaps to resolve before coding**
- Build plan explicitly blocks U4 on replacement, refund, moderation, and notification policies.
- D-04 defines a 30-day delivered return window and refund after simulated receipt/approval, but not reason catalog, return methods, replacement eligibility/stock behavior, rejection criteria, who advances return states, or notification semantics.
- Review moderation needs explicit initial status/publish policy, reporting workflow, content/media rules, and rate-limit behavior.
- Support needs a concrete proposal payload, supported deterministic actions, expiration/idempotency semantics, and issue-timeline retention model.
- U3's implementation state machine is narrower than architecture (`preparing → shipped → delivered` only); no `out_for_delivery`, delivery exception, or return-to-sender fixture exists. U4 should not invent those unless policy expands scope.
