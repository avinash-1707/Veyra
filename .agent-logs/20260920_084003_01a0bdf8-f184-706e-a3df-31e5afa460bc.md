## Bottom line

No implementation exists, but the documentation has several **High-severity launch blockers**. Most notably: unresolved auth/CSRF design, incomplete inventory-reservation lifecycle, unsafe/underspecified upload handling, and contradictory scope/acceptance definitions.

No Critical finding is confirmed because this is pre-build documentation.

## High

1. **Authentication, session, CSRF, and CORS are not implementation-ready**
   - **Sources:** `docs/specs/02_system_architecture_spec.md` — *Security and trust boundaries*, *Security operational requirements*; `docs/technical-architecture.md` §10; `docs/specs/04_design_decisions_log.md` ADR-004 / D-03.
   - The specs permit either cookie sessions or access/refresh tokens, and defer CSRF “according to D-03.” This is a security boundary, not a detail that can remain open once account and commerce mutations begin.
   - Missing: session lifetime/absolute expiry, rotation and revocation, logout-all-devices behavior, session fixation prevention, password hashing/recovery controls, verification policy, CSRF mechanism, same-site/cookie domain policy, approved CORS origins, and authentication rate-limit thresholds.
   - **Remediation:** Resolve D-03 before U0 with one concrete auth contract. If cookie-based, use `Secure`, `HttpOnly`, restrictive `SameSite`, origin checking plus CSRF tokens for unsafe methods, and session rotation on login/password change. Define recovery-token storage/expiry/single-use and session revocation.

2. **Guest-cart behavior contradicts the authorization rule and has no security model**
   - **Sources:** `docs/specs/01_product_ux_flow_spec.md` — *Route and state conventions* (`shopper or guest cart`); `docs/technical-architecture.md` §4.2 (`User/guest owner`), §6 (“All mutating endpoints require authentication”); `docs/specs/02_system_architecture_spec.md` — *Ownership and write rules*.
   - A guest cart necessarily permits unauthenticated mutations, while the API rule prohibits them. No opaque guest-cart credential, expiry, rotation, cart-claim/merge behavior, or anti-fixation rule is defined.
   - **Remediation:** Either require sign-in before any cart write, or define guest carts as bearer-owned resources using a high-entropy HttpOnly cookie, CSRF protection, expiry, rotation on login, and an explicit transactional merge/conflict policy. Never accept guest-cart IDs alone as authorization.

3. **Inventory reservation lacks a durable lifecycle and expiry executor**
   - **Sources:** `docs/technical-architecture.md` §4.2–4.3; `docs/specs/02_system_architecture_spec.md` — *Command and checkout contract*; `docs/specs/03_build_plan.md` U3.
   - The model only describes aggregate `warehouse_stock.reserved`; it does not define a reservation record with owner, quantity, quote/checkout reference, state, expiry, and release idempotency. Expiry is required, but no scheduled reaper/reconciliation process or recovery procedure is specified.
   - This risks permanently stranded stock, double-release, and incorrect availability after retries/crashes.
   - **Remediation:** Add an authoritative `inventory_reservations` model and state machine. In the checkout transaction, create a reservation tied to quote/order/idempotency key; make consumption/release idempotent; run a leased, observable expiry job; and periodically reconcile `reserved` counters against active reservations. Add crash-between-commit-and-worker and expiry-race tests.

4. **Review-media uploads are insufficiently protected**
   - **Sources:** `docs/technical-architecture.md` §10; `docs/specs/02_system_architecture_spec.md` — *External integrations*, *Security operational requirements*; `docs/PRD.md` §7 P0 Reviews and Q&A.
   - P0 includes review media, but signed URLs plus type/size validation do not prevent malicious content, cross-user object overwrite/read, executable SVG/HTML delivery, or publication before scanning. Scanning/moderation is conditional (“where enabled”), despite public user-generated media.
   - **Remediation:** Require server-authorized, short-lived, single-object upload grants scoped to a private quarantine prefix; validate claimed and detected content type/size; scan before promotion to immutable public media; serve through a separate media origin with safe content-disposition/CSP and no active formats unless transformed; bind finalization to the authenticated review draft. Define deletion and scan-failure handling.

5. **Personal-data governance is deferred despite P0 collection and third-party AI use**
   - **Sources:** `docs/specs/02_system_architecture_spec.md` — *Security operational requirements*, *AI evidence and safety contract*; `docs/technical-architecture.md` §10; `docs/PRD.md` §§7, 11.
   - The architecture says classification, retention, deletion/export, and incident response must be defined *before production*, but P0 already collects addresses, account data, browse/search events, reviews/media, support content, and sends evidence to an LLM provider. No data inventory, retention schedule, erasure propagation (PostgreSQL, Redis, Qdrant, object storage, logs, analytics), provider-processing boundary, or consent/control semantics is specified.
   - **Remediation:** Make this a U0 launch gate. Define data classes, purpose, access roles, retention, deletion/export SLA, backups/tombstone behavior, and redaction. Minimize/hash search and behavior analytics where possible. Specify what may enter LLM prompts, prohibit unnecessary address/order PII, and require provider DPA/retention/configuration approval.

6. **P0, milestones, baseline inventory, and acceptance criteria conflict**
   - **Sources:** `docs/PRD.md` §7 P0/P1, §12, §13; `docs/amazon-baseline-inventory.md` §§3–4; `docs/specs/00_project_overview.md` — *V1 scope* and *Scope guardrails*; ADR-005.
   - P0 checkout requires coupons/promotions and saved mock payment methods, while the inventory classifies coupons as “Later baseline” and the PRD places deals/coupons in P1. Initial acceptance requires natural-language search and fact-grounded comparison guidance, while the baseline-before-AI rule and Milestone 1 exclude AI and comparison. D-04 blocks tax/promotion policy, yet P0 requires displayed tax/discount totals.
   - This prevents an objectively shippable first release and invites teams to implement undefined policy.
   - **Remediation:** Define named releases (e.g., M1 baseline versus P0 complete release), assign each capability to exactly one, and rewrite §13 against that release. Until D-04 resolves, remove coupons/promotions/tax calculations from mandatory checkout or define an explicit single-locale configured policy.

## Medium

7. **Abuse and fraud controls are named but have no enforceable policy**
   - **Sources:** `docs/amazon-baseline-inventory.md` §7; `docs/technical-architecture.md` §10; `docs/specs/02_system_architecture_spec.md` — *Security operational requirements*.
   - “Basic rate limits” and “rules-based risk flags” do not define response actions. Missing protections include account-enumeration-safe login/recovery responses, signup/recovery throttles, credential-stuffing detection, per-account/device/IP limits, review-vote/review spam handling, coupon/gift-card abuse controls if enabled, and mutation velocity limits.
   - **Remediation:** Define endpoint-specific quotas and escalation actions (delay, CAPTCHA/challenge, temporary block, manual review), keyed by account and network/device signals with privacy limits. Ensure login, recovery, and account creation return non-enumerating responses. Add abuse metrics and alert thresholds.

8. **Order/return/refund state contracts are incomplete and partly inconsistent**
   - **Sources:** `docs/PRD.md` §§8.2, 9.3–9.4; `docs/technical-architecture.md` §7; `docs/amazon-baseline-inventory.md` §5.
   - Architecture shows cancellation only from `CONFIRMED`, although checkout/order wording also uses `PLACED`; the return model lacks explicit replacement lifecycle/linked replacement order; inventory calls for a refused refund state while the defined return state machine does not. Delivery exception and returned-to-sender outcomes do not define their effect on refunds, return eligibility, or order terminal state.
   - **Remediation:** Publish complete state diagrams and transition tables, including actor, authorization, preconditions, idempotent effect, terminal states, replacement linkage, refund failure/refusal/retry, and RTO handling. Tie policy values to D-04 rather than controller defaults.

9. **Outbox processing has no ordering, lease, retention, or replay policy**
   - **Sources:** `docs/specs/02_system_architecture_spec.md` — *Outbox delivery contract*; `docs/technical-architecture.md` §8.
   - Event IDs, retries, and deduplication are good foundations, but do not define worker leasing, concurrent claim behavior, per-aggregate ordering/version checks, duplicate-effect storage, dead-letter access control/retention, or replay impact on external/non-idempotent effects.
   - **Remediation:** Define an at-least-once delivery contract with row leasing/heartbeat, consumer inbox/deduplication keyed by event ID, aggregate sequence/version handling for ordered consumers, retention/archive rules, privileged replay tooling, and reconciliation metrics.

10. **Support conversations and AI evidence need explicit access and retention boundaries**
   - **Sources:** `docs/specs/02_system_architecture_spec.md` — *AI evidence and safety contract*; `docs/technical-architecture.md` §§5.4, 10; `docs/PRD.md` §9.4.
   - Support endpoints create conversations, but the data ownership, transcript retention, support-staff access model, prompt-injection handling for user-provided review/support text, and audit treatment of proposed versus confirmed actions are unspecified.
   - **Remediation:** Define conversation ownership and access roles; retain only needed transcripts; log proposal/action IDs without sensitive prompt bodies; treat user text and retrieved content as untrusted data, not instructions; permit only a fixed, server-enforced read-tool/action allowlist.

11. **Operational requirements lack measurable recovery and ownership criteria**
   - **Sources:** `docs/technical-architecture.md` §§9, 12; `docs/specs/02_system_architecture_spec.md` — *Deployment and operations*; `docs/specs/03_build_plan.md` U0.
   - Backups, health checks, rollback, and dead-letter visibility are required, but no RPO/RTO, backup frequency/retention, restore-test cadence, migration rollback compatibility window, alert thresholds, on-call owner, incident severity model, or dependency outage policy is defined.
   - **Remediation:** Resolve D-02 with a minimum operations runbook: service ownership, availability and latency SLOs, RPO/RTO, backup/restore tests, migration expand/contract policy, alerts for reservation leaks/outbox age/DLQ depth/error rate, and tested rollback/capability-disable steps.

12. **Acceptance criteria do not prove authorization, security, or operational safety**
   - **Sources:** `docs/PRD.md` §13; `docs/specs/03_build_plan.md` — *Cross-unit controls* and unit exit evidence.
   - The PRD acceptance list tests functional journeys but omits cross-user resource denial, session/CSRF behavior, upload quarantine, rate-limit behavior, privacy controls, reservation expiry/reconciliation, outbox replay, backup restore, and AI evidence leakage tests.
   - **Remediation:** Add release acceptance criteria for these controls, with executable fixtures and evidence. U3/U4 tests mention some cross-user and replay cases, but they should be release gates, not only work-package notes.

## Lower severity

13. **Search URLs, analytics, and logs may expose sensitive shopper intent**
   - **Sources:** `docs/PRD.md` §§9.1, 10; `docs/specs/01_product_ux_flow_spec.md` — *Route and state conventions*; `docs/technical-architecture.md` §11.
   - Search state is shareable in URLs and search/browse events are retained, but there is no rule for query-string logging, referrer leakage, analytics access, or sensitive-query retention.
   - **Remediation:** Avoid logging raw query strings by default; redact/hash or separately protect analytics values; use restrictive referrer policy; document retention/access; do not place account or address-derived state in URLs.

14. **Public versus account-owned resource enumeration needs endpoint-level rules**
   - **Sources:** `docs/specs/01_product_ux_flow_spec.md` — *Route and state conventions*; `docs/technical-architecture.md` §6.
   - UX correctly requires not exposing account-owned resource existence, but API behavior for IDs, list share links, review/media resources, and consistent `404`/`403` handling is not specified.
   - **Remediation:** Define authorization-first lookup behavior and uniform non-disclosing responses for owned aggregates. Use unguessable identifiers/share tokens where direct public sharing is supported.
