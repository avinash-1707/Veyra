## Proposed module split

### 1. Keep compatibility facades

Preserve these files and exports:

```txt
apps/api/src/modules/cart/cart.ts
apps/api/src/modules/orders/orders.ts
apps/api/src/modules/returns/returns.ts
apps/api/src/modules/discovery/discovery.ts
apps/api/src/modules/intelligence/intelligence.ts
```

Each facade should re-export from the new service/test-support files later:

```ts
export {
  readCart,
  addCartItem,
  updateCartItem,
  moveCartItem,
  removeCartItem,
  resetCartsForTests
} from "./service.js";
```

This preserves test imports and API behavior.

### 2. Move route registration out of `index.ts`, but keep `app` export

Target shape:

```txt
apps/api/src/index.ts
apps/api/src/routes/
  catalogRoutes.ts
  discoveryRoutes.ts
  cartRoutes.ts
  checkoutOrderRoutes.ts
  returnsReviewSupportRoutes.ts
  intelligenceRoutes.ts
```

`index.ts` remains the composition root:

```txt
index.ts
  create Hono app
  apply middleware
  register route modules
  export app/default app
```

Do not expose repositories to routes. Routes should only:

- parse request/query/body
- call service
- map command result to existing HTTP status/error envelope
- apply existing response schemas

## Transaction and idempotency boundaries

These are the important boundaries to preserve or tighten.

### Cart mutations

Boundary per command:

```txt
idempotency check/claim
  -> validate offer/variant availability
  -> insert/update/delete cart item
  -> read cart response
  -> persist idempotency response
```

Keep scope names stable enough for behavior:

- `cart:add`
- `cart:update:{lineId}`
- `cart:move:{lineId}:{location}`
- `cart:remove:{lineId}`

Repository should own storage mechanics; service should own command fingerprinting and conflict semantics.

### Checkout confirm

This is the most important transaction boundary.

One transaction should cover:

```txt
idempotency check/claim
  -> quote ownership + expiry check
  -> existing order by quote check
  -> simulated payment policy check
  -> inventory reservation updates
  -> order insert
  -> order_items insert
  -> payment_attempt insert
  -> shipment insert
  -> stock_reservations insert
  -> order_history/audit insert
  -> outbox_events insert
  -> idempotency response persist
```

Current behavior already does these writes, but not as one explicit transaction boundary. The split should make `confirmCheckout` the service-level transaction owner.

### Returns and reviews

Return creation transaction:

```txt
idempotency check/claim
  -> order ownership/read
  -> eligibility check
  -> duplicate active return check
  -> return_requests insert
  -> return_history insert
  -> audit insert
  -> outbox event insert
  -> idempotency response persist
```

Review submission transaction:

```txt
idempotency check/claim
  -> order ownership/read
  -> delivered policy check
  -> duplicate verified review check
  -> review insert
  -> outbox event insert
  -> idempotency response persist
```

### Support confirmation

This is a cross-domain command orchestrator. Keep it in `returns/service.ts` for now because support is grouped with returns/reviews.

Its idempotency boundary should wrap the selected action:

```txt
idempotency check/claim
  -> load proposal
  -> execute exactly one action:
       track order
       cancel order
       create return
       check refund
  -> mark proposal confirmed
  -> persist idempotency response
```

Avoid letting repositories call other domain repositories directly.

## Why this design

This is the smallest safe split because it:

- preserves current API routes, envelopes, schemas, and test import paths
- avoids premature package/module extraction
- keeps the modular monolith design from ADR-002
- makes transaction ownership visible at the service layer
- isolates PostgreSQL/in-memory fallback complexity in repositories
- avoids cyclic domain dependencies

Rejected for now:

- Full dependency injection container: too much structure for this codebase.
- Separate packages per domain: would churn imports/tests without changing behavior.
- Microservices/workers split: explicitly against current ADR unless scale/ownership changes.
