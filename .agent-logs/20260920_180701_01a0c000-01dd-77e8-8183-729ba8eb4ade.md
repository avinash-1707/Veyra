## Bottom line

Do not gate orders on `x-veyra-shopper-id`. Replace it with a server-resolved Better Auth principal, and keep guest carts as a separate anonymous, cookie-held capability that is explicitly claimed/merged after sign-in.

This milestone is blocked from being complete by Better Auth not being wired to any database adapter/schema or route handler, and by the absence of a disposable PostgreSQL integration test path.

## Context and assumptions

Facts from the current code:

- Orders and returns trust arbitrary `x-veyra-shopper-id` headers (`apps/api/src/modules/orders/route.ts`, `returns/route.ts`).
- Carts trust arbitrary `x-veyra-cart-id`; absent header uses one shared `local-guest-cart` (`apps/api/src/platform/routeHelpers.ts`).
- `createAuth()` only constructs config; it has no database adapter and is never mounted (`apps/api/src/modules/identity/auth.ts`, `apps/api/src/routes.ts`).
- The current `users`/`sessions` schema does not provide Better Auth’s credentials/OAuth/session records: no account or verification records, and session uses `token_hash` rather than Better Auth’s expected session shape (`packages/db/src/schema/users.ts`).
- Current tests use in-memory commerce state; they cannot prove a valid Better Auth database session.

## System design

```text
Anonymous browser
  └─ HttpOnly guest-cart cookie ──> anonymous cart

Authenticated browser
  └─ Better Auth session cookie ──> API resolves user from session
                                      ├─ owns user cart
                                      └─ POST cart claim: guest cart → user cart

Checkout/order/return routes
  └─ require resolved Better Auth user ID
     └─ never read shopper identity from a request header/body
```

### Minimal complete changes

1. **Make Better Auth real before protecting commerce**
   - Add a Drizzle database client/factory and configure Better Auth’s existing Drizzle adapter.
   - Mount Better Auth’s handler under its auth route prefix in Hono.
   - Apply a forward-only migration that makes the identity tables match the selected Better Auth adapter schema, including account and verification records required for credentials and Google OAuth.
   - Resolve ID compatibility deliberately: keep UUID user IDs only if the selected Better Auth configuration supports UUID generation/mapping; otherwise migrate identity IDs before identity data exists.

2. **Introduce one API-level principal resolver**
   - Resolve the session from the raw request cookies through Better Auth on every owned-commerce route.
   - Return `401 unauthorized` when absent/invalid. This requires an additive API-error/status contract update; current `fail()` and `ApiErrorCode` only support `403`.
   - Pass only `principal.user.id` into orders, returns, reviews, support, and idempotency scopes.
   - Remove `shopperIdFromRequest()` usage entirely from these routes. Keep `404` for cross-user resources to avoid ownership disclosure.

3. **Preserve guest carts without trusting headers**
   - Give each anonymous browser a high-entropy guest cart ID in an HTTP-only, Secure, SameSite=Lax cookie scoped to the API surface.
   - Continue cart operations without authentication using that cookie; do not use a client-selected cart ID as production identity.
   - Keep `x-veyra-cart-id` only in test helpers during transition, not as a browser-authoritative production path.
   - Replace the shared `local-guest-cart` default. It currently mixes all headerless shoppers.

4. **Claim/merge rather than silently replace**
   - Add an authenticated, idempotent `POST /v1/cart/claim` command. It reads the guest-cart cookie and session; it accepts no shopper or cart identity from the browser.
   - In one transaction: lock/read guest and user carts, merge matching offer/variant/location lines with the existing quantity ceiling, retain non-conflicting lines, mark the guest cart claimed, and clear/rotate the guest-cart cookie only after commit.
   - Make the merge retry-safe with a source-cart-to-target-cart claim record or equivalent durable state. Do not mutate on `GET /v1/cart`.
   - On merge failure, retain the guest cookie and cart unchanged so the shopper can retry.

5. **Bind checkout to the authenticated cart**
   - Quote creation uses the server-resolved user cart after claim, not a freely supplied `cartId`.
   - Quote and confirm persist the authenticated user ID; confirm re-resolves the session rather than trusting the quote caller.
   - User-scoped idempotency records must use the authenticated user ID.

## Why this design

It preserves anonymous shopping and avoids forcing sign-in before cart use, while ensuring that an authenticated order can only be created/read/changed by the user represented by a validated, revocable server-side session.

Rejected alternatives:

- **Continue `x-veyra-shopper-id` after login:** trivially impersonable.
- **Use a guest cart ID as the order owner:** does not meet authenticated-order requirements.
- **Automatically merge on cart read:** turns a safe read into a failure-prone state mutation and makes recovery opaque.
- **Build a custom session lookup over `sessions.token_hash`:** duplicates Better Auth behavior and leaves credentials/OAuth schema gaps unresolved.

## Hard blockers

1. **Identity implementation blocker — critical**
   `createAuth()` has neither a database adapter nor mounted routes, while current SQL/Drizzle identity tables are incompatible/incomplete for Better Auth credentials plus Google OAuth. No request can presently have a server-verified Better Auth session.

2. **Verification blocker — critical for milestone acceptance**
   There is no configured disposable PostgreSQL test database/branch/container. The current in-memory test path can test that routes reject headers, but cannot prove Better Auth-issued cookies resolve against its real schema and database adapter.

3. **Existing checkout atomicity gap — not caused by this milestone**
   Persistent confirmation reserves stock, then performs multiple order writes without one transaction (`apps/api/src/modules/orders/service.ts`, `repository.ts`). A failure can leave reservations without an order. This does not weaken session verification, but it prevents claiming full U3 transactional completion.
