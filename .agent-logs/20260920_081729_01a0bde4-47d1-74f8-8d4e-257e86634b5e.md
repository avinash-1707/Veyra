No external fetch is failing. I re-audited the docs locally.

**Verdict: solid foundation, but not fully build-ready for security/operations.** Rate limiting, authorization, idempotency, outbox retries, AI grounding, and simulated-payment boundaries are all present—but several need enforceable policies and acceptance tests before U0.

### Inconsistencies / scope gaps
1. **Customer support priority conflict**  
   - `docs/amazon-baseline-inventory.md`: customer service is **Baseline**.  
   - `docs/PRD.md`: customer service is **P1**.  
   Decide whether it is P0 or P1.

2. **Baseline features not assigned to a build unit or explicit deferral**  
   Includes save-for-later, open-order address/delivery edits, sponsored placements, gift cards, gift registries, and fuller notifications.  
   Add each to a milestone or `05_future_improvements_v2.md`.

3. **Commerce policy is unresolved but critical**  
   `D-04` correctly flags locale/currency/tax/promotions, but it also needs concrete cancellation cutoffs, return windows, refunds, replacement policy, inventory-reservation TTL, and delivery rule definitions before U1–U4.

### Security gaps to resolve before implementation
1. **Authentication/session contract** — `D-03` needs:
   - password hashing standard (Argon2id recommended);
   - verified-email and recovery-token lifecycle;
   - session rotation, idle/absolute expiry, logout/device revocation;
   - opaque authentication failure responses to prevent account enumeration;
   - CSRF model for cookie sessions, plus exact CORS/origin policy.

2. **Rate-limit and abuse policy**  
   Docs require rate limiting, but do not define quotas, keys, fallback behavior if Redis is down, or responses. Define separate limits for IP/account/session for login, recovery, registration, search suggestions, reviews, support, AI, cart, checkout, and confirmation endpoints. Include bot/credential-stuffing and AI-cost abuse controls.

3. **Authorization/admin boundary**  
   Shopper ownership checks are strong, but the plan does not define who can seed/publish catalog data, moderate reviews, operate workers, replay dead letters, or view audit data. Add a default-deny internal-operator role model and separate operational access path.

4. **Privacy policy and data lifecycle**  
   `02_system_architecture_spec.md` says to define classification, retention, deletion/export, and incident response—but none is yet defined. Block production personal-data/event collection until those policies, backup deletion behavior, and legal/jurisdiction requirements are selected.

5. **Media upload hardening**  
   Signed URLs and size/type checks are insufficient alone. Specify allowlisted MIME + magic-byte validation, malware scanning, quarantine-before-publication, object-key isolation, download/content-disposition policy, EXIF stripping, and authorization for private review media.

6. **AI/provider controls**  
   Good grounding protections exist. Add:
   - prompt-injection handling for reviews/catalog/user text;
   - provider data-retention/region/DPA decision;
   - per-user AI quotas, timeout/budget caps, circuit breaker;
   - evaluation thresholds that block release for unsupported claims.

7. **Supply-chain security**  
   Missing from coding standards: lockfile policy, dependency vulnerability scanning, secret scanning, SBOM/license review where applicable, and patch/upgrade ownership.

### Reliability / operational gaps
- Define backup **RPO/RTO**, restore-test cadence, incident severity/ownership, alert thresholds, and dead-letter replay authorization.
- Define cache TTL/invalidation ownership and prohibit PII/account-specific data in shared cache keys.
- Add API protections: request/body limits, pagination caps, search-query complexity limits, timeouts, and standardized error envelope.
- Add explicit tests for CSRF, cross-user access, session fixation/recovery flow, enumeration, rate-limit bypass, upload abuse, prompt injection, dead-letter replay, and backup restore.

### Already well covered
- Server-authoritative prices/inventory/orders.
- Transactional reservation, idempotency, outbox, and replay-aware workers.
- AI cannot mutate commerce state or decide money/policy.
- Authorization/non-disclosure requirements.
- Simulated payments and no card-data storage.
- AI fallback and conventional-flow continuity.

I recommend adding decision records `D-05` through `D-10` for auth/session, abuse/rate limiting, privacy retention, operator access, media security, and operational recovery before starting U0.
